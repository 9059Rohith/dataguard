# DataGuard Prometheus alert drill

DataGuard exposes bearer-protected metrics for database readiness, API work and persisted attempts. It also logs background database bootstrap retries without including connection credentials. The database alert can identify an outage while the exporter responds. The scrape alert covers a missing exporter or failed authentication through the `up` series generated by Prometheus. [Rules](../deploy/alerts.yml) · [Runbook](RUNBOOKS.md#metrics-scrape-failure) · [Prometheus scrape signals](https://prometheus.io/docs/concepts/jobs_instances/)

Prometheus 2.45.3 from the Ubuntu package scraped an isolated DataGuard process backed by local PostgreSQL 18.2. The drill loaded the repository's alert rules directly and retained both one-minute holds. It used 15-second scrapes, a 10-second scrape timeout and a two-second evaluation interval for the lab. The timings below are observed transitions in that configuration. [Prometheus alert rule timing](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)

| Fault | Observed rule sequence | Stop to observed firing | Restart to observed inactive |
|---|---|---:|---:|
| Stop PostgreSQL | `DataGuardDatabaseUnavailable` inactive → pending → firing → inactive | 76.85 s | 13.03 s |
| Stop the DataGuard API | `DataGuardMetricsUnavailable` inactive → pending → firing → inactive | 86.29 s | 5.67 s |

During the database outage, `/health` returned 200 and `/ready` returned 503. Authorized metrics returned 200 with `dataguard_database_up` equal to zero. The independent pinned replay still returned 500 real Apache repository records. Requests to `/metrics` without a token and with an incorrect token returned 401. Both recoveries returned readiness 200 and retained the original eight-record GitHub capture ID and SHA-256 fingerprint. The script also checked that the unrelated alert remained inactive during each sustained fault. [Observed states and timestamps](../evidence/prometheus-alert-drill.json)

The drill exercises evaluation and resolution in Prometheus. Notification routing to an external incident service is outside the drill. The Vercel application continues to serve the same runtime build because this change adds monitoring configuration and evidence.

## Reproduce locally

Use the locked DataGuard development environment, native PostgreSQL binaries, and the Ubuntu `prometheus` package extracted under `ubuntu/` in a dedicated `.vercel` work directory. Create a disposable PostgreSQL cluster under `.vercel` with local trust for the drill. Keep it stopped before running the harness. The harness chooses available local ports, creates a new test database, and stops its processes when finished. The bearer token is generated locally and removed from the scrape directory on exit.

```powershell
.\.venv\Scripts\python.exe -m scripts.run_monitoring_drill `
  --prometheus-workdir .vercel/dataguard-prometheus `
  --postgres-data .vercel/disposable-postgres `
  --postgres-bin 'C:/Program Files/PostgreSQL/18/bin' `
  --output .vercel/monitoring-observation.json
```

The standalone `promtool check rules` check accepted all three rules. The focused application suite passed 27 startup and request-boundary tests. [Executable drill](../scripts/run_monitoring_drill.py)
